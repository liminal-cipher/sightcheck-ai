# 시야체크 입력 자료와 경량 변환 API

2026.10.01 작성 · 2026.10.26 현재 코드 대조. 변환 응답 엔진은 0.2.0, 서버 health의 엔진 버전은 0.3.0이다.

## 현재 화면과 같은 결과를 얻기 위한 입력

현재 화면은 **실측 좌표에 공통 무대·조명·좌석 자산을 결합한 스타일 표현**이다. 실제 공연장의 모든 외관을 사진처럼 복원한 결과가 아니다. 이 수준의 보기 좋은 시야 시뮬레이션에는 Blender가 필요하지 않다.

| 자료 | 필요한 내용 | 현재 활용 | 누락 시 |
| --- | --- | --- | --- |
| 좌석 평면도 1장 | 정투영·균일 축척 PNG/JPEG/WebP, 무대 전면과 좌석 중심이 보임 | 로컬 OCR 후보 → 사람 확인 → 2D 좌표 | 축척 없는 예매 그림·원근 사진은 이 변환 경로 사용 불가 |
| 실제 거리 | 무대 전면 두 끝의 픽셀 좌표와 실제 폭(m), 무대 깊이 | 픽셀→미터 변환 및 무대 구성 | 거리 계산 불가, 실측 필요 |
| 높이 자료 | 좌석별 바닥 높이, 무대 바닥 높이, 분석할 전면 영역 높이 | 카메라 눈높이 및 가림 계산 | 좌석 높이를 0으로 임의 채우지 않음 |
| 가림 구조물 | 난간·기둥·타워·세트의 중심 좌표와 폭·높이·깊이, 공연 배치 | 화면과 광선 계산에 같은 박스 사용 | 현장 조사로 확인; 누락 구조물을 자동 발견하지 않음 |
| 현장 대조 사진 | 대표 좌석의 정면 사진, 좌석명·공연 배치·촬영일·눈높이·렌즈 정보 | 브라우저 사진 첨부와 운영자 대조 기록 | 결과는 검수 전 추정으로 유지 |

운영자가 가진 도면이 건축 PDF/DWG라면 우선 **동일 축척의 평면도 이미지를 추출**한다. 제품에는 PDF/DWG 자동 파서, 원근 보정, 여러 층 도면의 자동 정합이 없다. 별도의 [PDF 좌석도 추출 실험](../../experiments/seatmap-pdf/experiment-guide.md)은 제품 변환 경로에 통합되지 않았다. 현재 업로드 이미지는 최대 2,000px로 균일 축소하므로 **화면에 표시되는 이미지 좌표**를 사용한다. 원본 이미지에서 만든 좌표를 축소본과 섞으면 안 된다.

좌석 전체를 사진으로 찍을 필요는 없다. 파일럿에서는 난간 앞·뒷줄, 양끝, 기둥 옆 등 가림 경계의 대표 좌석 20개를 우선 대조한다. 사진 수는 복원 정확도를 보장하는 숫자가 아니라 첫 검수 계획이다. 촬영 시 카메라 위치·렌즈·수직 화각을 기록하고 비교 모델과 정렬한다. 스마트폰 '1배'가 수직 60°라는 뜻은 아니다.

## 입력 수준별 가능한 결과

| 입력 수준 | 가능한 결과 | 판단 |
| --- | --- | --- |
| 사진 한 장 | 외관 참고·현재 좌석의 실사진 안내 | 정확한 좌석별 3D 시야 생성 불가 |
| 축척 없는 예매 좌석도 | 좌석명 후보 추출 | 배열 그림의 간격을 실제 거리로 사용하면 안 됨 |
| 축척 도면 + 거리·높이 + 구조물 치수 | 경량 공간·좌석 카메라·고정 구조물 가림 | 이번에 구현한 경로 |
| 위 자료 + 대표 좌석 실사진 | 가림 오류 수정과 운영자 검수 | 유료 파일럿 전에 필요한 경로 |
| 겹쳐 찍은 다수 사진/영상 + 실측 기준 + 보정 | 사진 기반 외관 복원 후보 | COLMAP 등 별도 오프라인 파이프라인, 미구현 |

## 실행과 화면 흐름

설치 후 `npm run build`, `npm start`. 개발은 `npm run dev`로 동일 API를 사용한다. Node 서버는 기본적으로 `127.0.0.1:4173`에서만 열린다. 다른 포트는 `SIGHTCHECK_PORT` 환경변수로 지정한다. 빌드한 실행 ZIP은 Node.js만 있으면 실행할 수 있도록 변환 API도 번들한다.

공연장 관리 → 변환 예시 불러오기 → 도면의 좌석 중심·기준점·치수 확인 → 사용 권한 및 검토 체크 → 변환 API 실행 → 변환 모델로 시야 보기. 예시는 직접 제작한 가상 도면이다.

실제 도면은 도면 선택 → AI 문자·좌표 후보 추출 → CSV에서 문자 중심을 실제 좌석 중심으로 수정 → 바닥 높이·구역·행 입력 → 무대 두 끝 지정 → 치수·구조물 입력 → 변환한다. OCR 결과에는 높이를 넣지 않는다. 누락된 값을 사람이 채워야 한다.

API는 **원본 사진을 받는 무조건적 image-to-3D 생성 API가 아니다.** 브라우저에서 자료를 읽고 검토한 좌표·치수를 API에 전달하는 구조다. 변환 작업은 원본 이미지·요청을 저장하지 않는다. 기존 `/index.html`의 사진 대조 기록과 적용 모델은 해당 브라우저 `localStorage`에 저장한다. `/operator.html`에서 저장한 모델·사진·검수·게시 기록은 서버의 `data/` 또는 `SIGHTCHECK_DATA_DIR`에 보관한다.

## API 계약

### GET /api/health

`engineVersion: "0.3.0"`, `storage: "filesystem"`, 변환 한도 `maxSeats: 300`, 공연장 모델 한도 `maxVenueSeats: 5000`, `authMode: "local"` 또는 `"token"`을 반환한다.

### POST /api/v1/convert

`Content-Type: application/json`. 입력 예시는 [engine-demo.json](../../public/engine-demo.json)이다. 변환·시야 API도 운영자 인증을 적용한다. 기본 로컬 모드는 루프백에서만 접근하며, 토큰 모드는 로그인 세션 쿠키 또는 `Authorization: Bearer <token>`이 필요하다.

```json
{
  "inputType": "rectified_plan",
  "name": "우리 공연장",
  "image": {"width": 1000, "height": 930},
  "calibration": {
    "stageLeft": [242, 110], "stageRight": [758, 110],
    "stageWidthM": 8.6, "audienceSide": 1
  },
  "stage": {"depthM": 3.6, "heightM": 0.6, "targetHeightM": 2.4},
  "seats": [
    {"label": "A1", "xPx": 338, "yPx": 455, "floorM": 0, "section": "1층", "row": 0}
  ],
  "obstacles": [
    {"id": "rail", "name": "전면 난간", "position": [0, 2.9, 8.0575],
     "size": [8.75, 1, 0.1], "layout": "all"}
  ],
  "rightsConfirmed": true,
  "positionsReviewed": true,
  "measurementsReviewed": true
}
```

기준점은 평면도의 무대 전면을 바라볼 때 왼쪽→오른쪽이다. 이미지 y는 아래가 양수다. 두 점을 잇는 벡터를 이미지에서 오른쪽으로 90° 돌린 방향에 객석이 있으면 `audienceSide: 1`, 반대면 `-1`이다. 서버는 잘못된 방향의 좌석을 거부한다. 픽셀 간 거리 20 미만인 기준점, 잘못된 숫자·중복 좌석·미검토 입력도 거부한다.

월드 좌표는 m 단위이며 x=무대 좌우, y=지면 기준 높이, z=객석 방향이다. 무대 전면의 분석 평면은 `[0, stage.heightM + 0.08, -0.25]`에서 시작한다. 구조물 `position`은 중심이고 `size`는 폭·높이·깊이이다. 이 변환 경로의 `schemaVersion` 2는 축에 정렬한 불투명 박스를 사용한다. 별도 운영자 편집기의 `schemaVersion` 3은 회전 박스도 지원하지만 휘어진·구멍 난·유리 난간을 그대로 표현하지 못한다.

응답은 `model`(`schemaVersion` 2), `cameras`(좌석명·위치·정면 표적·수직 화각 60°·눈높이 1.2m), `report`(좌석 수·미터/픽셀·모델 JSON 크기·주의 조건)이다. `status`는 항상 `needs_site_review`. 이 응답이 현장 정확도를 인증하지 않는다. 외부 JSON에 `verified`를 넣어도 검수 완료로 신뢰하지 않는다.

현재 도면 변환은 평면 위치의 회전·이동·균일 축척 변환이다. 사진의 원근·국소 왜곡·늘어난 그림·층마다 다른 축척에는 적용할 수 없다. 서로 다른 층을 같은 이미지에 적절히 정렬해 준비하는 것도 현재는 운영자의 작업이다.

### POST /api/v1/sightline

```json
{"model": "변환 응답의 model 객체로 대체", "seatLabel": "C3", "layout": "theatre", "eyeHeightM": 1.2}
```

지원 배치는 `theatre`/`concert`, 앉은 눈높이는 0.9~1.45m다. 응답의 `visible`, `lowerVisible`은 25×13 표본의 비율, `angle`은 중앙축의 수평 각도(°), `causes`는 가림 원인별 표본 수다. `distance`는 `schemaVersion` 1·2에서는 수평 거리, 3에서는 눈 위치와 관람 대상 중심 사이의 3차원 거리(m)다. `schemaVersion` 3은 선택적인 `targetId`도 받는다. 무대 전체의 정확한 면적 비율·만족도·화면 안에 들어오는 영역의 비율이 아니다. 현재는 화각 안의 표본만 따로 걸러 계산하지 않는다.

HTTP 오류: 잘못된 JSON 400, 토큰 모드 인증 누락 401, 다른 출처 브라우저 요청 또는 로컬 접근 제한 403, 지원하지 않는 메서드 405, 3MiB 초과 413, JSON 외 형식 415, 입력 값 문제 422. 변환 API가 외부 URL을 요청하거나 원본을 보관하지는 않는다. 단일 운영자 인증과 파일 기반 검수·게시 저장소는 구현돼 있지만 사용자 계정·테넌트 격리는 없다.

## 경량화의 실제 의미

20석 예시 모델의 JSON은 약 2.3KB다. 이는 **좌표·치수 모델 데이터만의 크기**다. Three.js를 포함한 화면 JS, 스타일, OCR WASM·언어 모델까지 2.3KB라는 뜻은 아니다. 화면 JS와 OCR 파일은 최초에 별도로 읽으며 OCR은 실행할 때 내려받는다. 저장용 JSON을 변경하면 공통 자산으로 모든 좌석을 다시 표시한다.

공통 좌석 형상은 `InstancedMesh`로 재사용하고 화면 변화가 있을 때 렌더링한다. 도면 모델이 최대 300석을 수용한다는 입력 한도와, 실제 모바일 300석의 원활한 조작을 검증했다는 주장은 다르다. 대형 경기장에는 좌석 구역 분할·`LOD`·정적 이미지 캐시와 성능 실측이 추가로 필요하다.
