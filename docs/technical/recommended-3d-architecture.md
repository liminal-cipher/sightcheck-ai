# 시야체크 AI — 화질·정확도·운영비를 고려한 권장 3D 구성

2026-09-30 검토. 실제 공연장 자료와 기기 측정 전의 설계 권고이며, 성능 실적이 아니다.

## 결정

**공연장 공통 3D 모델 하나 + 좌석별 카메라 좌표 + 공연별 무대 배치**를 기본으로 한다. 좌석을 바꿀 때 같은 장면에서 카메라만 옮기므로 좌석별 이미지를 전부 제작할 필요가 없다. Three.js를 관객용 뷰어와 기본 배치 편집에 사용하고, Blender는 필요한 자산·재질·정적 조명 제작에 선택적으로 사용한다. 실제 사진은 검증과 재질 자료로 쓴다.

|---|---|---|---|

## 화질을 높이는 순서

1. **시야에 중요한 구조부터 맞춘다.** 좌석 중심·행 단차·눈높이·무대 위치·가까운 난간의 높이와 두께를 기록한다. 난간·기둥·스크린처럼 가림을 만드는 구조는 간소화하더라도 실루엣과 위치를 보존한다. 구조가 부정확한 장면은 고해상도여도 구매 판단 품질이 낮다.
2. **재사용 가능한 좌석 자산 하나를 만든다.** 박스 좌석을 등받이·방석 형태가 있는 간결한 모델로 바꾸고 반복 배치한다. 모든 좌석을 개별 고해상도 모델로 만들지 않는다. 좌석 색·벽·바닥·무대 재질을 실제 현장에 맞추면 적은 기하 구조로도 일관된 인상을 줄 수 있다.
3. **조명을 제한한다.** 기본 공간의 정적인 음영은 필요시 텍스처로 베이크하고, 공연별로 바뀌는 세트나 조명을 기본 베이크에 섞지 않는다. 모바일에서는 다수의 실시간 그림자·반사·후처리를 우선 피한다. Blender는 이 자산 제작 단계에만 써도 충분하다.
4. **중요한 곳에 해상도를 쓴다.** 가까운 난간과 무대는 선명하게, 멀리 있는 좌석·천장은 낮은 디테일로 표현한다. AI 재질을 쓴다면 난간·무대 윤곽을 바꾸지 않는 표면 자료로 제한하고 실제 관측 자료와 구분한다.
5. **A/B 비교 조건을 고정한다.** 같은 눈높이·화각·종횡비·무대 기준점을 사용한다. 좌석마다 무대를 화면 가득 확대하면 거리 차이를 숨길 수 있다. 실제 검증 사진의 렌즈·위치도 기록한다. 고정 화각의 시뮬레이션이라는 안내를 제공한다.

## 배포와 모바일

- 먼저 2D 좌석도와 공연 기본 정보를 띄우고, 3D는 선택 구역의 공통 자산을 점진적으로 읽는다. 공통 좌석·공연장 자산과 공연별 세트 데이터를 따로 캐시한다.
- 반복 좌석은 InstancedMesh, 큰 공연장은 구역 단위 로딩과 디테일 단계 조절을 사용한다. 인스턴싱만으로 기하 처리량·텍스처 비용까지 사라지는 것은 아니므로 함께 줄인다.
- 카메라·좌석 선택·배치가 바뀔 때 렌더링하고 정지 상태에서는 계속 그리지 않는다. 모바일 해상도와 그림자는 기기별로 조절한다.
- 텍스처가 병목이면 KTX2, 외부 모델 전송량이 병목이면 Meshopt/Draco를 검토한다. 압축은 디코딩 시간도 생기므로 작은 기본 모델에는 무조건 추가하지 않는다.
- A/B 비교는 가능한 한 같은 장면·자산과 WebGL 컨텍스트를 공유해 두 카메라로 그린다. 비교 패널마다 모델·텍스처를 다시 로드하지 않는다.
- 3D를 실행하기 어려운 기기에만 선택한 좌석의 전방 이미지를 요청한다. 서버는 요청된 좌석을 렌더링하고 반복 요청을 캐시한다. 모든 좌석을 사전 생성할 필요는 없지만, 서버 렌더링 비용과 최초 요청 지연은 측정해야 한다.
- 이미지 캐시는 공연장 모델 버전·공연 배치 버전·좌석·눈높이·화각·화질을 키로 삼는다. 무대 변경 시 해당 버전의 결과를 폐기한다.

360도 이미지는 관객이 통로·주변 구조를 확인할 때 선택 제공한다. 대표 좌석의 실사 파노라마를 옆 좌석의 정확한 시야라고 표시하거나, 서로 다른 좌석 사진을 보간해 검증 자료로 삼지 않는다. 하나의 360도 이미지에서는 머리를 돌려 볼 수 있지만 카메라 위치를 이동했을 때 생기는 시차·가림 변화는 재현할 수 없다.

## AI의 역할

좌석도 OCR → 행·열·구역 후보 추출 → 현장 자료에서 구조물 후보 제안 → 운영자 치수 입력·수정·승인 → 공통 모델 구축 → 승인 자료를 인용한 좌석 문의 답변. 여러 좌석의 시야 이미지를 생성 AI로 각각 꾸미는 것보다, **공통 모델을 만드는 수작업과 공연별 갱신 작업을 줄이는 AI**에 집중한다. 도면 이미지는 실제 공간과 비례가 맞지 않을 수 있고, 단일 사진의 깊이 추정에도 실측 보정이 필요하다.

시야 판정용 모델과 표시 모델은 같은 좌표·버전을 쓰고 난간 등의 실루엣이 어긋나지 않도록 확인한다. 실제 사진으로 검증한 좌석과 모델에서 추정한 좌석의 표시를 구분한다. 고정 구조의 가림 판정은 앞사람의 키·자세·이동이나 공연 연출의 보증이 아니다.

## 최적 여부를 확인할 실험

같은 공연장 1곳·대표 좌석 20개·무대 배치 2개에서 다음 세 가지를 동일 조건으로 비교한다: ① 간결한 도형 모델 ② 재질·음영을 개선한 공유 모델 ③ 사전 렌더링한 좌석별 이미지. 실제 좌석 사진은 별도로 확보한다.

측정값은 첫 유효 시야가 나타나는 시간, 좌석 전환 지연, 전송량, 조작 중 프레임 속도, 가능한 경우 메모리, 실제 사진 대비 가림 오류, 제작·갱신 작업 시간이다. 중급 모바일 기기와 성능이 낮은 기기에서 느린 네트워크·캐시 유무를 나눠 확인한다. 가림이 다른 사진으로 드러난 좌석은 원인을 수정하기 전까지 검증 상태로 공개하지 않는다.

초기 제품 목표의 예시는 첫 유효 시야 3초 이내, 모델 로드 후 좌석 전환 300ms 이내, 조작 중 30fps 이상이다. 이는 측정 환경을 지정해야 하는 **가설적 목표**이며 현재 달성 수치가 아니다. 공유 모델이 이를 달성하면 좌석별 파노라마를 기본으로 전환할 이유가 약하다. 실패한 기기는 정적 이미지로 보완한다.

## 공식 기술 근거

- [Three.js InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html): 반복 객체의 draw call 감소.
- [Rendering on Demand](https://threejs.org/manual/pages/rendering-on-demand.html): 변화가 있을 때 렌더링해 불필요한 전력 사용 감소.
- [KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html): 지원 GPU 압축 형식으로 텍스처 변환.
- [GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html), [DRACOLoader](https://threejs.org/docs/pages/DRACOLoader.html): 모델 압축 지원과 디코딩 비용.
- [LOD](https://threejs.org/docs/pages/LOD.html): 거리에 따른 상세 수준 전환.
- [Blender Render Baking](https://docs.blender.org/manual/de/3.2/render/cycles/baking.html): 정적인 음영·재질을 텍스처로 제작하는 기법.

결론은 **실측 치수로 보정한 공통 모델을 재사용하고, 선택 좌석의 카메라만 이동하는 Three.js 기반 구성**을 우선 검증하는 것이다. 화질 개선 자산과 대표 실사진을 보강하고, Blender·사진 복원은 그 과정에서 필요한 부분에만 적용한다.
